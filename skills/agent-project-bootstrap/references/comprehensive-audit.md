# Comprehensive Repository Audit

仅在首次接入或用户要求全面复审时使用。覆盖关键工程维度，不逐个读取全部文件，也不要求项目采用同一套工具。

## Establish the Evidence

先列出受版本控制的文件和顶层目录，识别 workspace、多模块和主要产物。没有版本控制时，限定在源文件和项目配置。

从 README、manifest、构建、测试、CI 和发布配置建立索引，再追踪代表性入口、模块、调用关系和测试。lockfile、大型文档与生成文件只提取必要信息。文档、配置和实际实现相互印证；有冲突、关键空白或高风险时才扩大读取范围或查相关历史。

对适用的维度确认事实，无法确认的标为未知；达到这一条件后停止探索：

- 项目目的、用户场景、稳定产品约束与交付形态。
- 语言、运行时、包管理器、依赖锁定、构建和启动条件。
- 模块职责、关键入口、权威配置及禁止编辑或生成区域。
- 数据与迁移、公共 API、兼容性、安全、性能、离线和部署边界。
- 分层测试、静态检查、CI、文档、许可、发布与回滚保障。
- 项目特有的高风险契约，例如公共库的发布产物、module metadata 和独立消费者验证，或共享状态的并发、生命周期和测试隔离。

完整项目画像留在回复或用户要求的报告中；只有符合入口文件准入条件的长期规则进入 `AGENTS.md`。

## Assess Readiness

将适用保障标为已覆盖、缺失、证据不足或不适用。先检查等价保障，不能仅因某工具、测试形式或部署方式不存在就判定项目不合格。

详细报告会影响决策的缺口：给出文件或检查证据、具体失败条件、实际影响、优先级和最小建议。合并简述不适用项，不为填充模板产生无关警告。

审计不自动授权安装工具、修复业务代码、增加 CI 或改变发布流程。已授权的补强按原任务范围完成；未授权的作为独立建议，不混入指引维护。
