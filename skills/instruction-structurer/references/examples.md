# 拆分边界示例

按当前疑问读取对应示例。这里展示语义结构的整理方法，不要求其他文档采纳示例中的政策。

## 独立阶段需要可发现的位置

原文：

> 提交前核对状态、实际待提交 diff 和验证，暂存后审查 staged diff 并运行检查，提交后报告 hash、message、剩余修改及是否已推送。

整理后：

```markdown
## 提交

### 提交前检查

- 提交前核对状态、实际待提交 diff 和验证结果。

### 暂存后检查

- 暂存后审查 staged diff 并运行检查。

### 提交后报告

- 提交后报告 hash、message、剩余修改及是否已推送。
```

三种执行阶段可分别定位。报告字段共同定义一次报告的内容，不必给每个字段单设分类。原文没有指定检查命令，不补写具体命令或新增推送要求。

## 条件与决策分支共同构成完整规则

原文：

> 若已有无关 staged 内容，先判断能否安全限定提交范围；能够限定时仅提交本任务内容，否则请求用户决定。

整理后：

```markdown
### 混合暂存内容的处理

- 若已有无关 staged 内容，先判断能否安全限定提交范围；能够限定时仅提交本任务内容，否则请求用户决定。
```

这里可以保留完整句子。条件、判断及两个分支共同定义一个决策；拆成无条件的“仅提交本任务内容”和“请求用户决定”会改变语义。仅浏览标题即可定位这项要求，无需为原子化再增加层级。

## 分类路径不能收窄通用约束

原文：

> 所有外部写入操作结果不明时，应先核对实际状态，再决定是否重试；Git push 也适用这条要求。

一种合适的结构：

```markdown
## 外部操作

### 写入结果不明时的重试判断

- 所有外部写入操作结果不明时，应先核对实际状态，再决定是否重试。

## Git

### Push

适用“外部操作 → 写入结果不明时的重试判断”。
```

如果只把整句放到“Git → Push → 重试”中，读者容易误以为规则只适用于 Git。集中定义保留了全部外部写入的范围，引用表达了 Push 的适用关系，也没有新增“永远不得重试”的禁止。

## 相似要求不一定等价

原文：

> 默认发布前需要人工批准。紧急修复获值班负责人批准后，可跳过常规发布审批，但仍须记录批准人。

可以组织为：

```markdown
## 发布

### 常规审批

- 默认发布前需要人工批准；紧急修复的例外见“紧急修复审批”。

### 紧急修复审批

- 紧急修复获值班负责人批准后，可跳过常规发布审批，但仍须记录批准人。
```

不能合并成“所有发布都必须走常规审批”，也不能缩写为“紧急修复无需批准”。这是明确的通用规则与例外；若原文另有“任何情况均不可跳过常规审批”且未说明优先级，应报告冲突而不自行裁决。
